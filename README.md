# Интернет-магазин «Web-Larёk»
«Web-Larёk» — это интернет-магазин с товарами для веб-разработчиков, где пользователи могут просматривать товары, добавлять их в корзину и оформлять заказы. Сайт предоставляет удобный интерфейс с модальными окнами для просмотра деталей товаров, управления корзиной и выбора способа оплаты, обеспечивая полный цикл покупки с отправкой заказов на сервер.

## Архитектура приложения

Код приложения разделен на слои согласно парадигме MVP (Model-View-Presenter), которая обеспечивает четкое разделение ответственности между классами слоев Model и View. Каждый слой несет свой смысл и ответственность:

Model - слой данных, отвечает за хранение и изменение данных.  
View - слой представления, отвечает за отображение данных на странице.  
Presenter - презентер содержит основную логику приложения и  отвечает за связь представления и данных.

Взаимодействие между классами обеспечивается использованием событийно-ориентированного подхода. Модели и Представления генерируют события при изменении данных или взаимодействии пользователя с приложением, а Презентер обрабатывает эти события используя методы как Моделей, так и Представлений.

### Базовый код

#### Класс Component
Является базовым классом для всех компонентов интерфейса.
Класс является дженериком и принимает в переменной `T` тип данных, которые могут быть переданы в метод `render` для отображения.

Конструктор:  
`constructor(container: HTMLElement)` - принимает ссылку на DOM элемент за отображение, которого он отвечает.

Поля класса:  
`container: HTMLElement` - поле для хранения корневого DOM элемента компонента.

Методы класса:  
`render(data?: Partial<T>): HTMLElement` - Главный метод класса. Он принимает данные, которые необходимо отобразить в интерфейсе, записывает эти данные в поля класса и возвращает ссылку на DOM-элемент. Предполагается, что в классах, которые будут наследоваться от `Component` будут реализованы сеттеры для полей с данными, которые будут вызываться в момент вызова `render` и записывать данные в необходимые DOM элементы.  
`setImage(element: HTMLImageElement, src: string, alt?: string): void` - утилитарный метод для модификации DOM-элементов `<img>`


#### Класс Api
Содержит в себе базовую логику отправки запросов.

Конструктор:  
`constructor(baseUrl: string, options: RequestInit = {})` - В конструктор передается базовый адрес сервера и опциональный объект с заголовками запросов.

Поля класса:  
`baseUrl: string` - базовый адрес сервера  
`options: RequestInit` - объект с заголовками, которые будут использованы для запросов.

Методы:  
`get(uri: string): Promise<object>` - выполняет GET запрос на переданный в параметрах ендпоинт и возвращает промис с объектом, которым ответил сервер  
`post(uri: string, data: object, method: ApiPostMethods = 'POST'): Promise<object>` - принимает объект с данными, которые будут переданы в JSON в теле запроса, и отправляет эти данные на ендпоинт переданный как параметр при вызове метода. По умолчанию выполняется `POST` запрос, но метод запроса может быть переопределен заданием третьего параметра при вызове.  
`handleResponse(response: Response): Promise<object>` - защищенный метод проверяющий ответ сервера на корректность и возвращающий объект с данными полученный от сервера или отклоненный промис, в случае некорректных данных.

#### Класс EventEmitter
Брокер событий реализует паттерн "Наблюдатель", позволяющий отправлять события и подписываться на события, происходящие в системе. Класс используется для связи слоя данных и представления.

Конструктор класса не принимает параметров.

Поля класса:  
`_events: Map<string | RegExp, Set<Function>>)` -  хранит коллекцию подписок на события. Ключи коллекции - названия событий или регулярное выражение, значения - коллекция функций обработчиков, которые будут вызваны при срабатывании события.

Методы класса:  
`on<T extends object>(event: EventName, callback: (data: T) => void): void` - подписка на событие, принимает название события и функцию обработчик.  
`emit<T extends object>(event: string, data?: T): void` - инициализация события. При вызове события в метод передается название события и объект с данными, который будет использован как аргумент для вызова обработчика.  
`trigger<T extends object>(event: string, context?: Partial<T>): (data: T) => void` - возвращает функцию, при вызове которой инициализируется требуемое в параметрах событие с передачей в него данных из второго параметра.

## Данные
В ходе анализа проекта было установлено: в приложении используются две сущности, которые описывают данные, — товар и покупатель.

### Интерфейс `IProduct` (Товар)
Описывает структуру данных отдельного товара в каталоге.

interface IProduct {
  id: string;
  description: string;
  image: string;
  title: string;
  category: string;
  price: number | null;
}
Назначение: Используется для хранения информации о товарах, доступных для покупки. Позволяет унифицировать данные, получаемые от сервера или хранящиеся в памяти приложения.

### Интерфейс `IBuyer` (Покупатель)
Описывает структуру данных о покупателе, необходимых для оформления заказа.

interface IBuyer {
  payment: TPayment | null;
  email: string;
  phone: string;
  address: string;
}
Назначение: Используется для хранения контактной и платежной информации пользователя на этапе оформления заказа.

### Интерфейс `ServerProductsResponse`

interface ServerProductsResponse {
  items: IProduct[];
  total: number;
}
Назначение: Описывает структуру JSON-ответа сервера при запросе списка товаров (GET /product). Гарантирует типобезопасность при работе с данными, полученными от бэкенда.

### Интерфейс `OrderPayload`

interface OrderPayload extends IBuyer {
  items: string[];
  total: number;
} 
Назначение: Описывает структуру данных (полезную нагрузку), которую фронтенд отправляет на сервер при оформлении заказа (POST /order).

### Интерфейс `OrderResponse`

interface OrderResponse {
  success: boolean;
  orderId: number;
  message: string;
} 
Назначение: Описывает структуру JSON-ответа сервера после успешной (или неуспешной) отправки заказа (POST /order). Позволяет фронтенду корректно обработать результат создания заказа и показать пользователю понятный статус.

### Модели данных
Для работы с данными в приложении реализованы три класса-модели, каждый из которых отвечает за свою зону ответственности.

### Класс `ProductCatalog` (Каталог товаров)

Зона ответственности: Хранение полного списка товаров, доступных в магазине, и управление состоянием отображения конкретного товара (детальная карточка).

Конструктор: constructor()
Не принимает параметров. Инициализирует внутренние хранилища: пустой массив `products` и значение `null` для `selectedProduct`.

Поля:
`products: IProduct[]` — массив всех товаров в каталоге. Отвечает за хранение актуального списка продукции, полученной от сервера или сгенерированной локально.
`selectedProduct: IProduct | null` — товар, выбранный пользователем для детального просмотра. Отвечает за состояние UI (какой товар сейчас открыт). Значение `null` означает, что детальный просмотр не активен.

Методы:
`saveProducts(products: IProduct[]): void`
    Назначение: Загружает или обновляет полный список товаров в каталоге.
    Параметры: `products: IProduct[]` — новый массив товаров.
    Логика: Полностью заменяет текущее содержимое поля `products` на переданное значение.
`getProducts(): IProduct[]`
    Назначение: Предоставляет доступ к текущему списку всех товаров.
    Возвращаемое значение:`IProduct[]` — массив товаров.
`getProductById(id: string): IProduct | undefined`
    Назначение: Поиск конкретного товара по уникальному идентификатору.
    Параметры:`id: string` — ID искомого товара.
    Возвращаемое значение: `IProduct | undefined` — найденный товар или `undefined`, если товар с таким ID не найден.
`setSelectedProduct(product: IProduct): void`
    Назначение: Устанавливает товар, который пользователь хочет рассмотреть подробно.
    Параметры: `product: IProduct` — товар для отображения.
    Логика: Записывает переданный товар в поле `selectedProduct`.
`getSelectedProduct(): IProduct | null`
    Назначение: Получает товар, который сейчас находится в режиме детального просмотра.
    Возвращаемое значение: `IProduct | null` — выбранный товар или `null`, если выбор не сделан.

### Класс `ShoppingCart` (Корзина)

Зона ответственности: Управление списком товаров, выбранных пользователем для покупки, отслеживание количества единиц товара и расчёт итоговой стоимости заказа.

Конструктор: constructor()
Не принимает параметров. Инициализирует внутреннее хранилище: пустой массив `items` для хранения товаров.

Поля:
`items: IProduct[]` — массив товаров, добавленных в корзину. Отвечает за хранение текущей сессии покупок пользователя. Каждый элемент массива представляет собой полную информацию о товаре согласно интерфейсу `IProduct`.

Методы:

`getItems(): IProduct[]`
    Назначение: Предоставляет доступ к текущему списку товаров в корзине.
    Возвращаемое значение: `IProduct[]` — массив товаров, находящихся в корзине на данный момент.

`addItem(product: IProduct): void`
    Назначение: Добавляет товар в корзину.
    Параметры: `product: IProduct` — товар, который нужно добавить.
    Логика: Проверяет, есть ли уже такой товар в массиве `items` (обычно по полю `id`). Если товар уже есть, логика может предусматривать увеличение количества (если бы у нас было поле `quantity` в модели корзины) или игнорирование повторного добавления. В текущей реализации просто добавляет товар в массив.
    Возвращаемое значение: `void`.

`removeItem(product: IProduct): void`
    Назначение: Удаляет указанный товар из корзины.
    Параметры: `product: IProduct` — товар, который нужно удалить.
    Логика: Находит товар в массиве `items` (по совпадению `id`) и удаляет его из списка. Если товар не найден, метод ничего не делает.
    Возвращаемое значение: `void`.

`clear(): void`
    Назначение: Полностью очищает корзину.
    Логика: Удаляет все товары из массива `items`, приводя корзину в исходное пустое состояние.
    Возвращаемое значение: `void`.

`getTotalPrice(): number`
    Назначение: Рассчитывает общую стоимость всех товаров в корзине.
    Логика: Проходит по всем товарам в массиве `items`, суммирует значения поля `price`. Если цена товара равна `null`, она трактуется как `0`.
    Возвращаемое значение: `number` — итоговая сумма заказа.

`getCount(): number`
    Назначение: Возвращает общее количество товаров в корзине.
    Логика: Возвращает длину массива `items`.
    Возвращаемое значение: `number` — количество позиций в корзине.

`hasItem(id: string): boolean`
    Назначение: Проверяет наличие товара с конкретным ID в корзине.
    Параметры: `id: string` — уникальный идентификатор товара.
    Логика: Ищет в массиве `items` товар, у которого поле `id` совпадает с переданным значением.
    Возвращаемое значение: `boolean` — `true`, если товар найден, `false` — если нет.


### Класс `BuyerData` (Данные покупателя)

Зона ответственности: Хранение, частичное обновление и валидация персональных, контактных и платёжных данных покупателя. Класс обеспечивает целостность данных при редактировании отдельных полей и предоставляет механизм проверки корректности заполнения формы перед оформлением заказа.

Конструктор: constructor()
Не принимает параметров. Инициализирует внутренние поля значениями по умолчанию: `payment` устанавливается в `null` (явно показывая отсутствие выбора), а текстовые поля (`email`, `phone`, `address`) — в пустые строки `''`. Такой подход позволяет чётко различать состояния «данные не введены» и «данные удалены».

Поля:
`payment: TPayment | null` — выбранный способ оплаты. Тип `TPayment` определяется отдельно. Поле хранит метод транзакции, выбранный пользователем. Значение `null` означает, что способ оплаты ещё не указан.
`email: string` — электронная почта покупателя. Поле используется для отправки чека и уведомлений. Изначально содержит пустую строку. Валидация требует, чтобы строка не была пустой.
`phone: string` — номер телефона покупателя. Поле необходимо для связи с клиентом при доставке. Изначально содержит пустую строку. Валидация требует, чтобы строка не была пустой.
`address: string` — адрес доставки. Поле содержит полный адрес, куда нужно привезти заказ. Изначально содержит пустую строку. Валидация требует, чтобы строка не была пустой.

Методы:
`updateData(data: Partial<IBuyer>): void`
    Назначение: Частичное обновление данных покупателя. Позволяет изменить только нужные поля, не затрагивая остальную информацию.
    Параметры: `data: Partial<IBuyer>` — объект, содержащий только те поля, которые требуется обновить. Использование типа `Partial` гарантирует, что можно передать даже один ключ (например, только `{ email: 'new@mail.com' }`).
    Логика: Метод перебирает переданные ключи и перезаписывает соответствующие поля в экземпляре класса. Если какое-то поле отсутствует в переданном объекте, его текущее значение остаётся неизменным.
    Возвращаемое значение: `void`.

`getData(): IBuyer`
    Назначение: Получение полного набора данных покупателя в формате, соответствующем интерфейсу `IBuyer`.
    Параметры: отсутствуют.
    Логика: Возвращает объект, содержащий текущие значения всех полей класса.
    Возвращаемое значение: `IBuyer`.

`clearData(): void`
    Назначение: Сброс всех данных покупателя в исходное состояние.
    Параметры: отсутствуют.
    Логика: Устанавливает поле `payment` в `null`, а все текстовые поля — в пустые строки. Используется, например, при отмене оформления заказа или выходе пользователя из сессии.
    Возвращаемое значение: `void`.

`validate(): Record<keyof IBuyer, string> | {}`
    Назначение: Проверка валидности всех обязательных полей данных покупателя.
    Параметры: отсутствуют.
    Логика:
        1.  Проверяет поле `payment`: если значение равно `null`, в результирующий объект добавляется запись `payment: 'Не выбран вид оплаты'`.
        2.  Проверяет текстовые поля (`email`, `phone`, `address`): если длина строки равна 0, в объект добавляется соответствующая ошибка (например, `email: 'Укажите email'`).
        3.  Поля, прошедшие проверку, не включаются в возвращаемый объект.
    Возвращаемое значение: Объект типа `Record<keyof IBuyer, string>`, где ключи — это имена полей, а значения — тексты ошибок. Если ошибок нет, возвращается пустой объект `{}`.

## Слой коммуникации

Этот слой отвечает за взаимодействие приложения с сервером. Он использует композицию: внутри него хранится экземпляр API-клиента, через который он делает запросы.

### Класс `DataService` (Слой коммуникации)

Зона ответственности: Обеспечение взаимодействия с внешним API (серверной частью). Выполнение HTTP-запросов (GET, POST) через базовый класс Api. Возврат сырых данных от сервера в строго типизированном виде. НЕ занимается бизнес-логикой, валидацией данных, сохранением данных в моделях или формированием сложных объектов из разных источников. НЕ зависит от конкретных моделей приложения (ProductCatalog, BuyerData, ShoppingCart).

Конструктор:
constructor(api: Api)

Методы:

`loadProducts(): Promise<ServerProductsResponse>`
Назначение: Выполнить запрос к серверу для получения списка товаров.

Логика: 1. Выполняет сетевой запрос: await this.api.get("/product"). 2. Не обрабатывает ответ, не проверяет наличие полей и не сохраняет данные в модели. 3. Возвращает ответ сервера «как есть», но с гарантией типа ServerProductsResponse.

Возвращаемое значение: Promise<ServerProductsResponse> — объект ответа сервера, который содержит поле items (массив товаров) и метаданные (например, total).

// Логика извлечения данных и сохранения лежит ВНЕ этого класса if (response.items.length > 0) { catalog.saveProducts(response.items); } ```

`sendOrder(payload: OrderPayload): Promise<OrderResponse>`
Назначение: Отправить готовый объект заказа на сервер.

Логика: 1. Принимает полностью сформированный объект заказа (payload) извне. 2. Выполняет сетевой запрос: await this.api.post("/order/", payload). 3. Возвращает ответ сервера с подтверждением создания заказа (OrderResponse).

Возвращаемое значение: Promise<OrderResponse> — объект с полями success, orderId, message.
Ключевое требование: Метод не собирает данные из моделей. Объект payload должен быть собран до вызова этого метода.

## Слой Представления(View)
Слой View отвечает за отображение данных и сбор действий пользователя. Он не содержит бизнес-логики (расчёт сумм, валидацию, запросы к серверу), а лишь транслирует события и отображает состояние, переданное из Презентера.

### Класс `Header` Шапка сайта и счётчик корзины.

Конструктор: constructor(events: IEvents, container: HTMLElement).

Поля:
protected events: IEvents — брокер событий для передачи действий в презентер.

### Презентер

В данном проекте слой Презентера реализован не в виде отдельного класса, а как центральный файл-диспетчер main.ts. Такой подход оправдан для приложений средней сложности: он позволяет избежать избыточной абстракции, сохраняя при этом четкое разделение ответственности.

Как работает Презентер
Логика работы построена на реактивной цепочке «Событие → Обработка → Обновление»:
Пользователь совершает действие (например, нажимает кнопку «Купить» в превью товара).
Компонент представления (Preview) генерирует событие cardButton:clicked и передает его в систему событий.
Презентер (main.ts) перехватывает это событие через events.on(...).
Презентер выполняет бизнес-логику:
Вызывает метод модели (cart.addItem(...)), который обновляет данные и эмитит внутреннее событие basket:changed.
Или подготавливает данные для следующей формы.
Презентер обновляет интерфейс:
Вызывает сеттеры в компонентах (например, header.counter = ...).
Или открывает новую модалку (modal.open() с новым контентом).
Модель уведомляет о изменениях: Если модель (например, BuyerData) меняет данные, она эмитит buyer:changed.
Презентер реагирует на изменение данных: Слушатель events.on('buyer:changed', ...) автоматически вызывает функции перерисовки форм (updateOrderForm, updateContactsForm), чтобы показать актуальные ошибки валидации или разблокированные кнопки.

Ключевые принципы реализации
Отсутствие генерации событий: Презентер только слушает события, но никогда не создает их сам. Это гарантирует, что источником истины всегда являются либо действия пользователя, либо изменения в модели.
Два триггера перерисовки: Интерфейс обновляется строго в двух случаях: 1. При событии от модели данных (buyer:changed, basket:changed), сигнализирующем об изменении состояния. 2. При явном событии открытия модального окна (basket:open, order:open).

Главное преимущество такой архитектуры в main.ts: Весь поток управления собран в одном месте. Чтобы понять, почему при клике на кнопку «Оформить» открывается форма контактов, достаточно посмотреть на один блок кода events.on('basket:open', ...) или events.on('order:submit', ...). Нет разбросанной логики по разным классам, и нет прямого вызова
